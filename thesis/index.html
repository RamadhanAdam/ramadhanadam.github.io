Reading malware like a map

Follow one suspicious file from the moment it lands in someone's inbox to the moment it gets a name, or gets flagged as something nobody has seen before. To the person using it, a malware detector is a black box: a file goes in, an answer comes out. This page opens the box. The file gets read two ways, turned into 128 numbers and placed on a map of the malware families the system knows. The card at the edge of the screen shows what the file has turned into at each step. Everything here moves, and you can pause it, step through it or play with it.

01 · the file arrives

Someone at work gets an email about an overdue invoice, with invoice.pdf attached. Windows hides the last part of a file's name, so they can't see that it's really invoice.pdf.exe: a program dressed up as a PDF, a PE file. Before anyone opens it, it goes through a detector. 02 · inside the file

A PE file is not a blob. It starts with a header, then a table of sections, then the sections themselves: .text holds the code, .rdata constants and the names of the functions it imports, .data its variables, .rsrc icons and other resources, .reloc fix-ups for the loader. Anything after the last section is the overlay. Click a region to look at its bytes.

The strip beside the file is entropy, from 0 (the same byte over and over) to 8 (indistinguishable from random). Code sits around 6. Packed or encrypted content runs close to 8, which is why a packed file glows.

The files in SOREL-20M and BODMAS are disarmed: two header fields, Machine and Subsystem, are set to zero so that they cannot run. Every other byte is the original. You can see the zeros in the header.

03 · two ways to read it

The file is read twice. Pipeline 1 measures it: EMBER's extractor turns it into a list of numbers about its header, sections, imports, strings and byte statistics. Pipeline 2 reads the bytes themselves, region by region. The two fail in different ways. A packer hides much of what the measurements describe, while the bytes still show what the file holds. Both end in the same place: 128 numbers that describe the file.

04 · from file to numberspipeline 1

EMBER describes a file with 2,568 numbers. They need cleaning before a network can use them. 706 columns are almost always zero or never change, so they go, leaving 1,862. A few header fields, such as the image base, reach values around 1012, so five columns are clipped and every value is squashed with a signed logarithm. Then each column is standardised with statistics from the training data only.

To learn without labels, the encoder is shown two views of the same file. Each view keeps about half of the features, the two views share three quarters of theirs, and in one view 60% of the shared values are swapped for values taken from other files. The encoder has to work out that the two views are the same file anyway.

05 · the feature enginepipeline 1

Each feature becomes a token. Its value goes through one shared layer into 512 numbers, and a learned embedding of the feature's index is added, so the engine knows which feature it is looking at even when a view has moved it. A [CLS] token goes in front. Six transformer layers, eight attention heads each, let every token look at every other. What comes out of [CLS] is squeezed to 128 numbers.

Letting every token look at every other has a price. With 931 tokens, a batch of 128 files and 8 heads, one layer's table of attention scores holds about 888 million numbers. Drag the slider to see how fast it grows, and whether it would still fit on a graphics card. FlashAttention computes the table in tiles and never keeps the whole of it, and activation checkpointing recomputes layers instead of storing them, which brought training down to about 10 GB.

06 · from file to regionspipeline 2

Pipeline 2 cuts the file along its own structure. Every region gets one of eleven types (header, the six common sections, other, overlay, unsectioned, and pad for empty slots), plus its entropy and its share of the file. A file keeps at most 16 regions: the header and overlay always, then the largest sections. From each region, up to four windows of 512 bytes are taken, spread from its start to its end. Every file becomes the same shape: 16 regions × 4 windows × 512 bytes.

The views here only take things away: some windows dropped, short spans hidden inside others, now and then a whole region removed. Removing bytes cannot invent content, so both views are still the same file. Two tiers that rewrite bytes were built and tested; they did not help, so training uses removal alone.

07 · the byte enginepipeline 2

The engine works from the bottom up. First, inside one window, each of the 512 bytes is looked up in a table of 257 rows (256 byte values and one for a hidden byte) and given its position. Two attention layers let the bytes look at each other, then a single learned query pulls them together into one vector of 128 numbers. The query decides which bytes matter.

The four window vectors of a region are averaged into one region vector. Then the regions look at each other through two more attention layers, with one addition: before the softmax, every pair of regions gets a bonus for being the same type, for having similar entropy and for having similar size. The three weights start at 1 and are learned. Move them, and click a region to see whom it pays attention to.

A masked mean over the real regions gives the file's 128 numbers. Padded slots are left out of attention and out of the mean.

08 · 128 numbers

Both pipelines end with 128 numbers for the file. Think of them as a fingerprint drawn as a strip: files of one family should produce similar strips, files of different families different ones. Nothing has told the encoders what a family is. The next stage is how they learned it anyway.

09 · learning without labels

Both encoders are trained the same way, on files nobody labelled: Pipeline 2 on the 19.7 million binaries of SOREL-20M, Pipeline 1 on EMBER. Each step takes a batch of files, makes two views of each, and runs them through the encoder and a small projection head. The loss pulls the two views of one file together and pushes them away from every other file in the batch. Families come out of that on their own, because files of one family share structure that survives the damage. Press play and watch the map organise itself; colour shows the families the encoder never sees.

10 · known or unknown

Each known family becomes a few landmarks, its prototypes. A family can be two clumps, so one average would sit in the empty space between them; HDBSCAN finds the clumps, and each gets a prototype. A family can also be stretched, so distance is measured in units of the family's own spread (Mahalanobis distance) instead of a plain ruler.

A file goes to its nearest family, and is rejected as unknown if it is farther away than that family's threshold. Thresholds belong to families, because families differ in spread, and each is set by fitting a Weibull curve to the tail of the family's own distances. Drag the file around, and try the three things under the map; they tick themselves off.

    11 · from unknown to a new family

    Rejected files are not dumped in a pile. HDBSCAN groups them by density, with no preset number of groups, and each group is shown to the analyst once, through its medoid, the member closest to all the others. When the analyst confirms a group, its files become the examples of a new family: the prototype is their average, built from one to twenty examples. Nothing is retrained. The next file of that family is recognised.
